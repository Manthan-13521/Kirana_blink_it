# Shopkeeper usability

Safari showed the hosted owner account with short, task-based sections for Overview, Orders, Catalog & stock, Counter sales, Reports, Support & refunds, Store settings and Team access. Browser emulation checked dashboard entry and page width across desktop, Android, iPhone and tablet profiles. Local fixture journeys covered the main sales and fulfillment tasks.

The timed two-store rehearsal produced independent, empty application configurations and databases with disjoint Worker and Pages names, six unique database identifiers, distinct per-store hostnames and order acceptance disabled. It excluded demo and benchmark entry points and generated configuration without embedding provider secrets. Cloudflare provisioning, owner/rider invitation, Google, Razorpay, Geoapify and branding with a second real merchant still require an independent hosted setup rehearsal. Local bundle time measures only local prep.

Actual shopkeeper acceptance is outstanding. Have a shopkeeper complete an assisted first run and then repeat without help, using the [handover guide](SHOPKEEPER_HANDOVER.md). Record task completion and where the owner asks for help. Use the synthetic store for practicing orders, refunds and catalog changes.
